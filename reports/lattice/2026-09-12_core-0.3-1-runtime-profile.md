## Why

The 2026-09-12 physical MkI pass refined CORE's failure mode:

- CORE sounds good and the maximum-TIME loop/freeze behavior is musically useful;
- distortion is intermittent at or near maximum TIME rather than a permanent high-TIME failure;
- CORE can also distort in some multi-effect combinations, while some runs remain clean;
- lowering source level in an earlier probe did not remove the high-TIME distortion.

The existing host chain probe also showed ordinary CORE microloop work continuing during settled freeze even though the frozen-loop path owns the audible result. The goal of 0.3-1 is therefore to reduce demonstrably unnecessary runtime work without changing the approved CORE identity, gain structure, patterns, history length, freeze sound or FIELD 0.1-2.

## What changed

### Ordinary microloop ceiling

`kMaxVoices` is reduced from **16 to 10**.

TIME still has a true disengaged region below the existing threshold and still increases ordinary microloop density across the control range, but the upper population now saturates at ten voices. High non-freeze TIME reaches the ten-voice ceiling before the maximum-TIME freeze region.

No changes were made to:

- wet drive formula;
- pattern tables;
- interval rules;
- stochastic scheduling rules;
- loop-length rules;
- capture-age rules;
- Q15 history format or 65536-sample history;
- freeze history length/crossfade;
- output guard/soft limiter.

### Freeze runtime suspension

When `s_freeze_active` is true, the ordinary microloop engine now performs **no**:

- new capture scheduling;
- wait countdown;
- microloop history reads;
- grain-window rendering;
- ordinary voice phase advancement;
- repeat retirement/rescheduling;
- ordinary wet accumulation.

Ordinary voice state is retained and resumes after freeze release. The freeze path continues to replay recent history exactly as the current architecture intends.

The history buffer was already stopped during freeze in 0.3-0; that behavior is unchanged.

## Sound-quality intent

The user explicitly likes CORE's current sound and maximum-TIME looping behavior. 0.3-1 is therefore intentionally conservative:

- preserve the existing sonic architecture;
- reduce only the highest ordinary density population;
- preserve the frozen-loop path rather than simplifying it;
- avoid global attenuation or FIELD degradation as a workaround.

The expected tradeoff is slightly less simultaneous microloop density at the upper non-freeze TIME range. Musical acceptance still requires physical listening.

## Runtime/headroom intent

This build is a runtime diagnostic, not proof that device CPU load caused the distortion.

It removes two concrete workload sources:

1. worst-case ordinary microloop processing falls from sixteen simultaneous voice states to ten;
2. ordinary microloop work becomes zero while full freeze is active.

There is still no ARM cycle measurement or MkI CPU telemetry. A clean hardware result would support the workload hypothesis; a continued failure would point toward granular playback structure, level interaction, or another hardware-only condition.

## A-class test changes

The CORE project-specific harness asserts:

- hard ten-voice ceiling;
- high non-freeze TIME reaches the ten-voice ceiling;
- maximum TIME still engages freeze and stops history writes;
- while freeze is active, event count, repeats, waits and ordinary microloop phases do not advance;
- frozen history remains audible into silence;
- freeze release resumes history acquisition;
- lifecycle reset remains clean;
- long parameter/freeze abuse remains finite and bounded.
